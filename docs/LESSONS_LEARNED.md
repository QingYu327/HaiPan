# 经验与教训 · 海畔

> 这里只写「下次能直接复用」的判断依据与踩坑记录；接口细节见 [ARCHITECTURE.md](ARCHITECTURE.md) 与 `api-handoff/`。

## 1. 认证、账号与设备

### 1.1 清空应用数据 = 销毁设备私钥
- 私钥在 Android Keystore，清空数据/卸载会重新生成密钥对；服务端旧公钥与新公钥不一致。
- 管理员身份是在**签发令牌之后**才由会话判定的，设备绑定发生在令牌之前——不能假设“管理员天然放行”。
- 现行策略：名单内学号公钥不一致时自动覆盖绑定，并作废旧会话（单设备生效）；管理页仍可手动重置。
- 教训：任何“本机密钥 + 服务端绑定”的设计，必须预留**恢复路径**（自动重绑、管理端重置或恢复码），否则用户清一次数据就永久锁死。

### 1.2 错误要分层，不要一律包装成“隧道失败”
- 设备认证拒绝曾发生在 `/device/register`，但客户端统一上报为「隧道建连失败」，排查时极易误判为网络问题。
- 现行做法：服务端 4xx 保留原始 `DioException` 上抛，登录页区分“学号验证失败”与“通道连接失败”；4xx 不进入重试循环。
- 教训：认证、隧道、目标站错误要分开上报；永久错误（4xx 业务码）不要进入重试循环。

### 1.3 管理员兜底要前后端一致
- 客户端对 `ownerXh` 有 APP 门控例外，服务端有 `ADMIN` 白名单例外；但两边都不能绕过设备认证，必须显式处理。

### 1.4 wfw 只能当“页面外壳”，登录提交必须走 original authserver
- CAS 的 ticket 与 `service` 参数绑定：用 `service=wfw` 拿到的票换不出 jw 的会话，“借 wfw 的票登录教务”走不通。
- `wfw.gdou.edu.cn` 是学校的 WebVPN 网关：GET 页面和静态资源会被改写成 `wfw/https://authserver...`，所以登录页能打开；
  但**登录 POST 不可靠**——提交后持续弹回登录页，页签仍指向 `authserver` 绝对地址，且页面上看不到任何错误提示。
- 现行：登录页直接用 `authserver.gdou.edu.cn/authserver/login?service=…jw…`（校外经隧道，页面无改写、页签是相对路径），
  CAS 回跳 jw 后读取 `JSESSIONID`；**不再使用 wfw 入口**，其兜底逻辑已删除。
- 实测：登录页经隧道首包约 **11s**（要拉几十个静态资源），加载超时必须 ≥40s，否则页面还没出就被判超时。
- 教训：判断“公网可达”要用 HTTPS(TCP 443) 多节点 + 真机分运营商验证；只看 HTTP(80) 的 302、或拿单台手机的一次拒连就下全局结论，都会误判。

### 1.5 反向 bypass 只放真正不可达的域名
- `ProxyController.setProxyOverride` 的 bypass 列表是“走代理”的名单，不是“直连”名单；多放一个可公网直连的域名，就多一份隧道流量与延迟。
- 现行放 `jw.gdou.edu.cn` + `authserver.gdou.edu.cn`：
  - jw 公网不可达，必须走隧道；
  - authserver 部分运营商直连会被拒，登录页与提交一并交给隧道最稳（代价是首包约 11s）。
- `wfw.gdou.edu.cn` 不进 bypass（原本直连，现已不作为登录入口）。

## 2. 公网隧道与高延迟

### 2.1 每次请求重建隧道代价过高
- 高延迟链路（1000ms+）上，握手 + 认证的成本会被放大；连接池、预热、复用是必要优化。
- 实测日志：容器重启后 `tunnel open` 163 / `tunnel close` 160，接近 1:1——功能没错，但每个 CONNECT 都在重付 TCP+TLS+WS 握手。
- 现行方案：`/tunnel-mux` 用一条长连接 + `streamId` 承载多条 TCP 流，20s 心跳保活；客户端保留单流模式作为回退。
- 刷新令牌/入口列表要加**闸门**：串行、限频、失败退避，避免并发风暴把隧道打满。

### 2.1.1 复用通道必须有回退
- 新旧客户端/服务端会短暂并存，复用握手失败时不能把登录链路一起弄坏。
- 做法：复用不可用立即回退单流模式，并冷却 3 分钟再试；协议本身用独立路径 `/tunnel-mux`，旧服务端返回失败不会影响 `/tunnel`。

### 2.2 关闭时序会丢数据
- WebSocket 与本地 Socket 转发时，直接 `destroy()` 会丢掉“响应后立即断开”的末尾数据（教务 302 尤其明显）；正确顺序是 flush → 写 Close 帧 → `end()`。

### 2.3 入口切换要防抖
- 多入口测速切换的条件要保守（不可达、明显更快才切），并限制测速频率，否则延迟抖动会导致频繁切换、体验更差。

### 2.4 备用通道协议必须与本地服务一致
- ME Frp 隧道若配成 HTTPS，而本地是明文 HTTP，会出现 `tls: first record does not look like a TLS handshake`，公网表现为 502。
- 教训：排障时同时看「边缘状态码」和「隧道客户端日志」，不要只盯应用层。

## 3. 部署与运维

### 3.1 `build: .` 的镜像，restart 不会更新代码
- 改 `server.js` 后必须 `docker compose up -d --build`；`docker restart` 只是重启旧镜像。
- 验证方式：`docker exec <容器> grep -c "<新代码标记>" /app/server.js`，不要凭“我重启过了”判断。

### 3.2 部署目录以 compose label 为准
- 实际目录是 `/vol1/1000/docker/haipan-api`，而同级的 `/vol1/1000/docker/haipan` 是另一份旧副本；改错目录会“怎么重建都不生效”。
- 排查命令：`docker inspect <容器> --format '{{ index .Config.Labels "com.docker.compose.project.working_dir" }}'`。

### 3.3 覆盖前先备份
- 远端 `server.js` 覆盖前保留 `server.js.bak-<说明>`；数据卷 `./data` 必须持久化并有定时备份。

### 3.4 凭据管理
- SSH 口令等临时凭据放 `.secrets/`（已 gitignore），文件头标注敏感与销毁条件；项目结项后删除。
- 文档、日志、提交信息中不出现明文口令；学号在日志中统一脱敏。

## 4. UI 与桌面小部件

### 4.1 小部件字号不要跟高度走
- 同宽的两个组件（4×2 与 4×3）如果按高度分档，字号会不一致，视觉上像两个 App。
- 结论：**宽度定字号，高度定行数**；行数按可用高度估算并留余量，超出显示「还有 N 门」。

### 4.2 尺寸声明要与内容匹配
- 用 `targetCellWidth/Height` + `minWidth/minHeight` 声明默认尺寸；仅课表 4×2、完整 4×3，可自由拉伸。
- `previewImage`/`previewLayout` 能提高在小组件面板中的可见性；新增组件后桌面可能需要刷新一次才会出现。

### 4.3 空余空间要给“有用信息”
- 排版留白不如补信息：明天第一门课、下一场考试；两者都按剩余高度决定是否显示，不能挤掉当天课程。

### 4.4 RemoteViews 的限制
- 不能用自定义 View/复杂动画；字号、可见性都要在 Provider 里动态设置；文本溢出用 maxLines + ellipsize，不依赖缩放。

### 4.5 小窗/分屏没有边缘返回手势
- 自由窗口与分屏下，左缘拖拽常被窗口管理器占用，只靠 `_EdgeBackSwipe` 的二级页会“进得去出不来”。
- 结论：二级页必须有一个**可见的返回按钮**兜底，手势只是增强，不能是唯一入口。

### 4.6 加载态不要直接暴露底层错误
- 冷启动时通道/会话还没就绪，请求会瞬时失败；把 `DioException` 之类原样显示，用户会以为 App 坏了。
- 做法：首屏失败先保持加载动画并自动重试，多次失败再给友好文案；错误详情只进日志页。

## 5. 数据口径与缓存

### 5.1 学业“未修/在读”看 `XDZT`
- `XNMC/XQMMC` 为空不能用来区分；`XDZT=4/1/3` 才是权威口径。

### 5.2 聚合接口宁可慢也要求准
- 学分计划并发请求会被服务端偶发丢弃，导致 GPA/通过数跳变；改为串行 + 重试后稳定。
- 聚合数据要带“结果指纹/去重键”，避免同名课程被误合并。

### 5.3 缓存键必须版本化并按账号隔离
- 改判读口径必须升级缓存键（如 `cache_academic_v2_...`），否则旧错误数据会一直被读到。
- 换账号要清 `cache_*`，否则 B 会先看到 A 的数据；准入缓存也要按学号隔离。

### 5.4 分页与查询语义
- jqGrid 默认只返回前 20 条，必须读 `records/total` 翻页并去重。
- 空教室多选在服务端是 AND，客户端要做“单时段逐查合并(OR)”并限速，避免被判异常。

### 5.5 并发汇总不能用共享集合长度判断成功
- 多个 worker 同时向 `all` 追加时，`all.length > before` 会被其他 worker 的新增误判为“本次成功”，导致空结果不重试。
- 必须用**本次响应局部计数**（如 `added`）判断成败；并发只改调度，不改判定口径。

### 5.6 高延迟下用“有界并发 + 失败重试”
- 3000ms 往返时，10+ 个串行请求就是几十秒；全并发又可能被服务端丢弃整组数据。
- 折中：固定 3 路并发、错开起步，空结果串行重试；仍不稳定就降到 2 路。

## 6. 流程与协作

### 6.1 上下文会压缩，记录必须即时
- 每次改动完成就写 `docs/modification_log.md`（范围、文件、验证、构建号、部署结果），不要等“有空再补”。
- 架构性决策同步进 `ARCHITECTURE.md`；踩坑结论进本文件。

### 6.2 先讲清流程，再动代码
- 涉及登录/认证这类高风险链路，先向用户复述现状流程与根因，确认方案后再改，避免“改了半天不是那个问题”。

### 6.3 验证链固定
- `flutter analyze` → `flutter test` → `build apk --release --target-platform android-arm64` → 真机安装 → 关键路径手测。
- 后端改动：`node --check` → 备份 → 上传 → `up -d --build` → 容器内 grep → 接口探测。

### 6.4 真机与模拟器要分清架构
- arm64 包不能装进 x86 模拟器（`UnsatisfiedLinkError`）；模拟器验证用 `android-x64`。

### 6.5 版本判断必须用安装包实际构建号
- 手写 `appVersion` / `appBuild` 会与 `--build-number`、Release tag 漂移；漏改一次，已是最新的用户就会被提示更新。
- 现行：`BuildInfo` 从原生 `appInfo` 读取 `versionName` / `versionCode`；`UpdateCheckResult` 用 `hasUpdate` / `isCurrent` 显式表达结果，首页只在 `hasUpdate && downloadUrl` 时弹窗。
- 发布前跑 `tool/check_version.ps1 -Tag v<版本>+<构建号>`；不要在同一个 tag 下替换不同构建的 APK。

### 6.6 静态官网也要按页面验收
- 单页拆成多页后，桌面导航与移动端菜单都要检查文档/注意事项入口；≤860px 用菜单按钮收纳，不能只靠会被隐藏的桌面链接。
- 资源路径用相对路径（`assets/...`），三页共享 `pages.css` / `pages.js`；上线前检查 `scrollWidth == clientWidth`、无破图、无重复 ID、控制台无报错。
- 官网部署仓库与 App 仓库的 `site/` 要同步，避免 Netlify 拉到的版本与本地不一致。
